# План переноса backend-сервисов с Railway

Статус на 2026-09-08: NestJS API временно переносится с Railway на Amvera. Позднее
NestJS API и отдельный Fastify backend планируется последовательно перенести на VDS.
Neon остаётся внешней базой данных.

Документ сохраняет только исходные измерения, критерии выбора и будущую схему
развёртывания. Подробный VDS-runbook нужно подготовить отдельно перед фактическим
переносом.

## Исходные измерения

Показания Railway за последний месяц оценены по графикам, поэтому значения
приблизительные. Пики около линий deployment могут включать одновременно старую и
новую реплики: Railway в режиме `Sum` складывает их потребление.

| Сервис | Обычная RAM | Пик вне deployment | Наблюдаемый максимум | CPU |
| --- | ---: | ---: | ---: | --- |
| Fastify backend | 60–75 МБ | около 80 МБ | 125–130 МБ | почти без нагрузки |
| NestJS API | 90–125 МБ | около 150 МБ | около 220 МБ | почти без нагрузки |

Зафиксированный baseline существующего VDS со статикой и Nginx:

- RAM: 956 МБ всего, 204 МБ занято, 751 МБ доступно;
- swap: 1 ГБ, занято 17 МБ;
- CPU: 99,2% idle, load average `0.18 / 0.13 / 0.10`;
- диск: 9,8 ГБ всего, 5,2 ГБ занято, 4,2 ГБ доступно;
- Nginx: около 16 МБ RSS; Docker пока не установлен;
- крупнейшие каталоги: `/usr` 2,9 ГБ, `/var` 892 МБ;
- журналы: `/var/log` 260 МБ, из них systemd journal 190,5 МБ.

Вывод: по CPU и RAM этот VDS способен обслуживать оба backend-сервиса при текущей
нагрузке. Узкое место — диск на 10 ГБ и кратковременный расход RAM при сборке или
одновременном запуске старых и новых контейнеров.

## Ближайшее решение: Amvera

Для NestJS выбран тариф **«Начальный»**: 0,25 vCPU, 500 МБ RAM и 5 ГБ SSD за
290 ₽/30 дней по тарифам на дату этого документа. «Пробный» с 100 МБ RAM ниже
измеренного обычного и пикового потребления и не подходит.

Если временно разместить в Amvera и Fastify, ему также безопаснее «Начальный»:
наблюдаемый максимум выше лимита «Пробного». Два таких приложения стоят около
580 ₽/30 дней. Перед подключением второго сервиса цену и лимиты нужно проверить
повторно: тарифы меняются.

## Будущий выбор VDS

| Вариант | Плюсы | Минусы | Когда выбирать |
| --- | --- | --- | --- |
| Один VDS от 2 ГБ RAM и 20 ГБ диска | общий запас ресурсов, один Docker/Nginx/monitoring, проще сопровождение | единая точка отказа | предпочтительно для небольшого MVP, если сервисы могут иметь общий maintenance window |
| Два недорогих VDS, по одному на сервис | изоляция отказов и независимые релизы | две ОС забирают больше суммарных ресурсов, двойная настройка и мониторинг | если важнее изоляция или сервисы принадлежат разным продуктам |
| Текущий VDS 1 ГБ/10 ГБ | дополнительных расходов нет, RAM пока достаточно | мало места для Docker-образов и логов; тесно для zero-downtime и локальных сборок | допустим как временный MVP после увеличения диска либо при строгом контроле места |

Оценка двух приложений вместе с текущей системой и Docker: 435–555 МБ RAM обычно,
до 504–674 МБ при наблюдавшихся пиках. Это не гарантия: перед покупкой VDS нужно
повторить замеры Railway/Amvera за 30 дней и провести smoke/load test контейнеров.

Цены около 150 ₽ за каждый будущий VDS — предварительная пользовательская оценка,
а не зафиксированный тариф. Сравнивать нужно итоговую цену с IPv4, диском, бэкапами
и трафиком.

## Целевая схема deployment

```text
push в main
  → CI: тесты и сборка multi-stage Docker image
  → публикация image с тегом commit SHA в GHCR
  → VDS скачивает готовый image
  → migration выполняется ровно один раз
  → перезапуск только нужного сервиса
  → /health/ready и smoke-check
  → при ошибке возврат на предыдущий image digest
```

На VDS не устанавливать Node.js/pnpm и не выполнять `npm ci`, `npm run build` или
`docker compose build`: сборка может исчерпать 1 ГБ RAM. Серверу нужны Docker Engine,
Compose plugin, Nginx, Certbot и существующие security-компоненты. Секреты Neon и
GHCR хранятся вне репозитория; пользователь CI не должен получать общий доступ к
Docker socket, эквивалентный root. Для deployment следует сделать root-owned script
с минимальным набором разрешённых команд.

В Compose предусмотреть:

- внутренние порты backend, доступные снаружи только через Nginx;
- `restart` policy, healthcheck и явные memory limits;
- ротацию `json-file` логов, например `max-size: 10m`, `max-file: 3`;
- образы по неизменяемому commit SHA/digest, а не только `latest`;
- последовательное обновление сервисов на малом VDS.

## Очерёдность переноса на VDS

1. **Подготовка платформы.** Выбрать один или два VDS, проверить свободные RAM/диск,
   установить Docker/Compose, настроить ограниченный deploy-доступ, Nginx, TLS,
   firewall, резервное копирование конфигурации и мониторинг. Использовать существующие
   [runbook безопасного доступа](vds-secure-access.md),
   [security/resource baseline](vds-security-resource-baseline.md) и
   [HTTP-платформу](vds-http-platform.md), расширив их для контейнеров.
2. **Сначала NestJS.** Добавить Dockerfile и CI для `main`, перенести variables,
   проверить Neon migrations/readiness, запустить контейнер без переключения DNS,
   выполнить smoke-check, затем переключить API-домен. Amvera оставить доступной для
   быстрого отката до окончания периода наблюдения.
3. **Стабилизация.** Не менее недели наблюдать RAM, swap, диск, restart count,
   latency/error rate и Neon connections. Устранить рост памяти и логов до второго
   переноса.
4. **Затем Fastify.** Повторить тот же pipeline независимо; не переносить оба сервиса
   одним изменением. После smoke-check переключить его DNS и оставить предыдущую
   площадку доступной на время отката.
5. **После переноса.** Удалять старые площадки и образы только после подтверждённого
   периода стабильности; зафиксировать рабочие image digests и процедуру rollback.

## Минимальный мониторинг и пороги решения

Для VDS с 1–2 ГБ не размещать локально полный стек Prometheus + Grafana + Loki.
Достаточно `node_exporter` с внешним хранилищем/дашбордом, внешнего uptime-check для
`/health/ready` и внешнего error tracking (например, Sentry).

Повод увеличить ресурсы или разделить сервисы:

- `MemAvailable` устойчиво ниже 200 МБ либо swap постоянно растёт;
- OOM/restart контейнера;
- диск занят более чем на 80–85% или свободно менее 1,5 ГБ;
- CPU продолжительно близок к лимиту вместе с ростом latency;
- memory usage растёт между deployment без возврата к baseline.
