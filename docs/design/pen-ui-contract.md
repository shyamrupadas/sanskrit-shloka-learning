# pen.dev UI-контракт

Сохраненный `design/pen-design.pen` — единственный утвержденный визуальный
источник истины для пользовательских экранов, состояний, reusable-компонентов и
визуальных токенов. Сохранение файла владельцем продукта означает, что дизайн
принят. Функциональное поведение определяют specs, доменные документы, ADR и
API-контракт.

Внутреннее содержимое `.pen` нельзя читать, искать или менять через shell,
обычные file readers, patching или другие raw-инструменты. Проверка наличия,
переименование и Git status допустимы как непрозрачные файловые операции.

## Read-only доступ

Факты о сохраненном дизайне получают через глобальный headless CLI
`pen interactive`:

- канонический файл передается только как input;
- output всегда является уникальным временным `.pen` в системной временной
  директории и удаляется после сессии;
- CLI agent mode не используется;
- `save()` внутри сессии может записать только временный output;
- отсутствие CLI или готовой авторизации является blocker без raw fallback.

Headless CLI используется только для чтения утвержденного состояния. Он не
является способом изменить канонический дизайн и не служит prerequisite для
live-редактирования через MCP.

## Изменение дизайна

Дизайн меняют только live через MCP-сервер `pencil` при запущенном Pen Desktop.
Такая задача начинается сразу с MCP; предварительный запуск или preflight CLI не
требуется:

Desktop-интеграцию предоставляет глобальная конфигурация pen.dev. В проектной
конфигурации нельзя фиксировать machine-specific executable path для этого MCP;
переносимые project MCP servers остаются project-scoped.

1. Получить editor state вместе со schema и подтвердить, что активен
   `design/pen-design.pen`.
2. Изучить релевантные screens, variables, reusable-компоненты и patterns;
   переиспользовать существующую дизайн-систему.
3. Вносить изменения инкрементально. Новые visual tokens, компоненты или
   patterns добавлять только при недостаточности существующих и явно показать
   владельцу. Внешние style presets не применять без отдельного поручения.
4. Для изменённого `ref` зафиксировать ожидаемые descendant paths и свойства,
   явно задать overrides и до screenshot проверить effective subtree через
   `resolveInstances: true`. Имя `ref` и screenshot не доказывают корректность
   скрытых `content`, `enabled` или typography properties.
5. Проверить релевантный layout на clipping/overlap и получить screenshot
   законченного screen или component.
6. Не вызывать сохранение. Сообщить владельцу, что canvas готов и не сохранен,
   затем остановиться до human review.
7. После подтверждения сохранения перечитать изменённые узлы через read-only
   launcher; для `ref` повторить exact `resolveInstances`-проверку. При
   расхождении вернуться в live-ветку и повторить handoff: переход к коду,
   закрытие задачи или design exception запрещены. Оставшийся только live
   descendant update исправить пересозданием `ref` с явным `descendants`.

Закрытый Desktop, недоступный MCP или неверный активный документ являются
blocker. CLI и raw-инструменты не могут быть fallback для записи. Только
владелец продукта принимает и сохраняет canvas; после его явного подтверждения
и успешной read-only проверки можно продолжить кодовую часть исходной задачи.
Перед code phase сохранённое утверждённое состояние перечитывают один раз.
Design-only поручение не расширяется до изменения кода.

## Видимые frontend-изменения

Перед началом code phase нужно через read-only CLI перечитать релевантные узлы
сохраненного дизайна. Повторное чтение требуется только после того, как владелец
принял и сохранил следующее изменение дизайна в рамках той же задачи. Имена и
`nodeId` из spec/ticket служат адресами, но не кешем свойств. Статическая карта
узлов не ведется: актуальные references получают напрямую через Pencil tools и
фиксируют в конкретной задаче как `## pen.dev references`.

## Backend/API-only задачи

Backend/API-only задача не обязана ссылаться на дизайн, если меняет только API,
доменную логику, данные, фоновые процессы или внутреннюю инфраструктуру и не
вводит новый видимый пользовательский сценарий.

Если backend/API-задача вводит будущий пользовательский сценарий, видимый
статус, экранный шаг или действие, родительский spec/ticket должен либо содержать
актуальные pen.dev references, либо явно отложить frontend-реализацию до
подготовки UI-контракта и решения возможного `UI Contract Collision`.

Если нужного screen/state/component нет или визуальный контракт противоречит
функциональному требованию, кодовую фазу останавливают с `UI Contract Collision`:

```md
## UI Contract Collision

- Требование: ...
- pen.dev reference: "..." (...) или not found
- Расхождение: ...
- Варианты решения:
  1. Обновить дизайн: ...
  2. Изменить требование: ...
  3. Разрешить design exception: ...
- Рекомендация агента: ...
```

Намеренные расхождения допустимы только по явному решению владельца и
фиксируются в [реестре исключений](./pen-ui-contract-exceptions.md). Нерешенные
коллизии остаются в соответствующих specs/tickets.

## Responsive/overflow решения

Мелкие responsive/overflow-адаптации допустимы по существующему pen.dev-паттерну,
если они не меняют функциональность, иерархию экрана, визуальную систему или
набор состояний. К ним относятся переносы длинного текста, разумные `min/max`
ограничения, scroll/overflow для длинных списков и сохранение читаемости на
мобильных размерах.

Нужно вернуть `UI Contract Collision`, если решение добавляет или убирает
controls, меняет смысл действия или иерархию экрана, вводит состояние, заменяет
reusable-компонент другим pattern либо требует новых visual tokens.

После реализации запускают обязательные frontend-проверки и сопоставляют
screenshot/export релевантного pen.dev-узла со screenshot работающего приложения
через Playwright MCP в том же viewport и состоянии. Review оценивает композицию,
размеры, spacing, typography, colors и states; pixel-perfect diff не требуется.

Если screenshot приложения получить нельзя, задача остается на visual
verification gate. Владелец может закрыть gate явным подтверждением собственной
ручной проверки. Это указывают в отчете задачи, но не создают UI-contract
exception.

Финальный отчет по видимой UI-задаче перечисляет использованные pen.dev
references, примененные exceptions и сообщает, кем выполнен visual review —
агентом или владельцем продукта.
