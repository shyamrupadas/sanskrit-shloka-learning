# 02 — Оформить известные UI Contract Collision для недостающих pen.dev-состояний

**What to build:** Подготовить проверяемые записи по уже известным расхождениям между функциональными требованиями и pen.dev UI-контрактом, чтобы последующие UI-срезы не решали недостающие состояния молча. Срез должен зафиксировать, где дизайн отсутствует или недостаточно точен, какие есть варианты решения для владельца продукта и какие будущие frontend-tickets должны остановиться без принятого решения.

**Blocked by:** None — can start immediately

**Status:** awaiting-human-review
Accepted: 2026-07-10

- [x] Для раскрытого состояния пачки повторения после `Показать еще N` оформлен `UI Contract Collision`.
- [x] Для раскрытого состояния списка шлок к заучиванию после `Показать все` оформлен `UI Contract Collision`.
- [x] Для специфичных пустых состояний вкладок `Повторяю` и `Буду учить` оформлен `UI Contract Collision` или явно указано, что используется общий `Product / Empty State`.
- [x] Каждая collision-запись содержит требование, pen.dev reference, расхождение, варианты решения и рекомендацию агента.
- [x] Связанный task context показывает эти collision как известные блокеры для будущих UI-задач.
- [x] Ни одно недостающее состояние не реализуется в коде в рамках этого среза.
- [x] Последующие ticket-файлы фиксируют принятые решения или ссылаются на актуальную запись реестра исключений.

## Результат

Первоначально были оформлены три проверяемые collision-записи. Последующий
аудит актуального дизайна, кода и принятых решений зафиксировал текущее
состояние:

- раскрытые списки после `Показать еще N` и `Показать все` разрешены владельцем
  продукта и перенесены как `UIE-003` в
  `docs/design/pen-ui-contract-exceptions.md`;
- пустые состояния вкладок используют общий `Product / Empty State` (`RPtlw`)
  и больше не являются collision или exception;
- статическая карта удалена, а нерешенные будущие collisions должны оставаться
  в соответствующих specs/tickets.
