# Безопасный workflow pen.dev UI-контракта

Status: ready-for-agent

## Problem Statement

Владелец продукта регулярно сначала дорабатывает канонический `.pen`-макет,
визуально принимает его в Desktop-приложении и только после этого разрешает
агенту приводить frontend-код в соответствие с утвержденным дизайном. Текущий
repository workflow не фиксирует эту последовательность как единый исполняемый
контракт: агент может попытаться прочитать или изменить `.pen` обычными файловыми
инструментами, выбрать headless CLI там, где нужна live-приемка, начать менять код
до утверждения макета либо закончить UI-задачу без визуального сравнения реализации
с дизайном.

Существующая статическая карта Pencil-узлов дублирует структуру канонического
дизайна и уже демонстрирует дрейф относительно принятых решений. Она также
противоречит выбранному правилу получать факты о `.pen` только через editor engine
pen.dev. Одновременно project-scoped MCP-конфигурация содержит абсолютный путь к
старому Desktop-приложению Pencil и устарела сразу после переименования приложения
в Pen, тогда как само pen.dev уже управляет актуальной глобальной конфигурацией
рабочей машины.

Без отдельного workflow правила будут либо разбросаны между длинными документами,
либо повторяться в каждой задаче. Это создает риск непреднамеренной записи в
канонический дизайн, реализации по неутвержденному canvas, появления скрытых
расхождений между дизайном и кодом и накопления design exceptions как удобного
обходного пути.

## Solution

Проект получает единый pen.dev UI-contract workflow с тремя уровнями. Компактное
repository instruction направляет релевантные задачи к project skill
`$pen-ui-contract`; человекочитаемый design workflow фиксирует обязательную
политику; skill выполняет режимную процедуру работы с pen.dev CLI, Desktop MCP и
Playwright MCP.

Read-only задачи читают только сохраненный и утвержденный `.pen` через headless
`pen interactive`. Безопасный helper всегда использует канонический дизайн как
input и отдельный временный output, поэтому даже ошибочный `save()` не может
перезаписать источник истины. Изменение дизайна выполняется только через MCP-сервер
`pencil` при запущенном Pen Desktop и правильном активном документе. Агент
проверяет layout и screenshot, не сохраняет документ и останавливается до
визуальной приемки владельцем продукта. Только владелец сохраняет утвержденный
макет; после явного подтверждения агент может продолжить кодовую часть исходной
задачи.

Каждая задача, создающая или меняющая видимый frontend UI, перечитывает
релевантный утвержденный дизайн через headless CLI, реализует код по актуальному
контракту и визуально сопоставляет screenshot приложения из Playwright MCP со
screenshot/export соответствующего pen.dev-узла. Pixel-perfect сравнение не
требуется. Невозможность воспроизвести состояние создает явный visual verification
gate, который владелец может закрыть собственной ручной проверкой.

Статическая карта узлов удаляется: имена и `nodeId` получаются напрямую через
Pencil tools. Актуальные намеренные расхождения между дизайном и кодом хранятся в
отдельном минимальном реестре exceptions, проходят начальный аудит и удаляются при
первой возможности синхронизировать дизайн и реализацию. Проектная терминология и
канонический design artifact переходят с legacy Pencil naming на pen.dev naming;
внешние идентификаторы MCP и названия сторонних источников сохраняются без
искусственного переименования.

## User Stories

1. Как владелец продукта, я хочу, чтобы агент изменял канонический дизайн только через Pen Desktop MCP, чтобы я видел изменения live на canvas.
2. Как владелец продукта, я хочу лично принимать каждое изменение дизайна до реализации, чтобы неутвержденный макет не становился основанием для кода.
3. Как владелец продукта, я хочу единолично сохранять измененный `.pen`, чтобы сохраненный файл всегда означал утвержденный источник истины.
4. Как владелец продукта, я хочу, чтобы агент явно остановился после изменения дизайна, чтобы у меня была реальная возможность проверить результат до продолжения.
5. Как владелец продукта, я хочу после сообщения об утверждении и сохранении продолжить первоначальную задачу в том же thread, чтобы не создавать искусственно отдельную задачу для кода.
6. Как владелец продукта, я хочу читать утвержденный дизайн без запуска Desktop-приложения, чтобы обычные implementation и review задачи не требовали GUI.
7. Как агент, я хочу использовать headless pen.dev CLI для read-only доступа, чтобы получать структуру, variables, layout и изображения из того же editor engine.
8. Как агент, я хочу запускать read-only CLI через безопасный helper, чтобы опечатка в output path не могла перезаписать канонический дизайн.
9. Как агент, я хочу получать понятный blocker при отсутствии глобального `pen` CLI, чтобы не переходить к raw-разбору `.pen`.
10. Как агент, я хочу получать понятный blocker при неготовой CLI-аутентификации, чтобы не подменять штатный Pencil tool workflow обходными командами.
11. Как агент, я хочу перед изменением дизайна проверять соединение с MCP, активный документ и его schema, чтобы не редактировать другой canvas.
12. Как владелец продукта, я хочу, чтобы закрытый Desktop, неверный активный документ или недоступный MCP останавливали изменение дизайна, чтобы агент не выбирал скрытый fallback.
13. Как владелец продукта, я хочу запретить raw-чтение `.pen` через shell, grep и обычные file readers, чтобы факты о дизайне всегда интерпретировались editor engine pen.dev.
14. Как владелец продукта, я хочу запретить raw-редактирование `.pen`, чтобы структурный UI-контракт нельзя было повредить обычной текстовой правкой.
15. Как владелец продукта, я хочу запретить headless CLI как способ изменения канонического дизайна, чтобы любое изменение проходило live-review в Desktop.
16. Как агент, я хочу использовать CLI agent mode только вне этого workflow по отдельному явному поручению, чтобы отдельный AI-агент pen.dev не вмешивался в read-only анализ.
17. Как дизайнер продукта, я хочу, чтобы агент сначала изучал существующие screens, reusable-компоненты и variables, чтобы изменения продолжали текущую дизайн-систему.
18. Как дизайнер продукта, я хочу переиспользовать существующие tokens и patterns, чтобы макет не накапливал визуальные дубли.
19. Как дизайнер продукта, я хочу видеть новые visual tokens, reusable-компоненты и patterns до сохранения, чтобы осознанно принимать расширение дизайн-системы.
20. Как дизайнер продукта, я хочу запретить неявное применение внешних style presets к существующему продукту, чтобы агент не подменял принятый визуальный язык.
21. Как владелец продукта, я хочу, чтобы агент проверял измененный layout на clipping и overlap до моей приемки, чтобы не тратить review на очевидно сломанный canvas.
22. Как владелец продукта, я хочу видеть законченный измененный screen или component на canvas до сохранения, чтобы визуально оценивать реальный результат.
23. Как frontend-разработчик, я хочу перед каждой видимой UI-правкой читать актуальный сохраненный design node, чтобы ticket references не подменяли полный визуальный контракт.
24. Как frontend-разработчик, я хочу использовать имя и `nodeId` из spec/ticket как адрес узла, а не как кеш его свойств, чтобы реализация опиралась на последнюю утвержденную версию.
25. Как автор spec или ticket, я хочу получать актуальные pen.dev references напрямую из сохраненного `.pen`, чтобы не поддерживать отдельную карту узлов.
26. Как reviewer, я хочу, чтобы UI-задача содержала точные человекочитаемые pen.dev references, чтобы быстро открыть проверяемые screens, states и components.
27. Как reviewer, я хочу сопоставлять screenshot работающего frontend со screenshot утвержденного design node, чтобы проверять визуальное соответствие, а не только успешную сборку.
28. Как reviewer, я хочу проверять композицию, размеры, spacing, typography, colors и states без обязательного pixel-perfect diff, чтобы review оставался содержательным и практичным.
29. Как владелец продукта, я хочу вручную закрыть visual verification gate сообщением, что проверил интерфейс и он корректен, чтобы локальные ограничения test data не блокировали готовую работу.
30. Как reviewer, я хочу видеть в финальном отчете, выполнял ли visual review агент или владелец продукта, чтобы не заявлять непроверенную синхронность.
31. Как frontend-разработчик, я хочу остановить реализацию, если нужного состояния нет в design contract, чтобы не импровизировать новый UI только в коде.
32. Как владелец продукта, я хочу выбирать между изменением дизайна, изменением требования и явным exception при UI Contract Collision, чтобы агент не принимал продуктовые решения молча.
33. Как владелец продукта, я хочу разрешать новое расхождение только явно, чтобы exception не становился быстрым обходом нормального design-review цикла.
34. Как сопровождающий проекта, я хочу хранить только актуальные намеренные UI-contract exceptions, чтобы будущий агент не исправил одобренное расхождение как случайную ошибку.
35. Как сопровождающий проекта, я хочу указывать для каждого exception причину, релевантный design reference, затронутую реализацию и условие удаления, чтобы долг можно было целенаправленно закрыть.
36. Как сопровождающий проекта, я хочу удалить устаревшие и уже устраненные exceptions при внедрении workflow, чтобы новый реестр начинался с минимального реального остатка.
37. Как сопровождающий проекта, я хочу получать node inventory через Pencil tools вместо статической карты, чтобы не синхронизировать вручную второй источник данных.
38. Как сопровождающий проекта, я хочу хранить Desktop MCP в глобальной конфигурации рабочей машины, чтобы переименование приложения не ломало committed project config.
39. Как агент, я хочу получать project skill только для задач, связанных с `.pen`, pen.dev references или видимым UI, чтобы подробная процедура не загружалась в несвязанных backend-задачах.
40. Как сопровождающий проекта, я хочу использовать актуальную терминологию pen.dev во всех активных проектных артефактах, чтобы legacy Pencil naming не создавало ложного различия между старым и новым workflow.
41. Как сопровождающий проекта, я хочу сохранить внешнее имя MCP-сервера и tool namespace, пока их задает pen.dev, чтобы внутренний ребрендинг не ломал интеграцию.
42. Как сопровождающий проекта, я хочу, чтобы repository instructions содержали только короткий trigger skill, чтобы корневые правила оставались компактными.
43. Как агент, я хочу читать policy-документ как источник обязательных инвариантов, а skill — как процедуру выполнения, чтобы правила и tool recipes не смешивались.
44. Как владелец продукта, я хочу линейный workflow без draft-статусов и параллельной оркестрации, чтобы сохраненный `.pen` оставался единственным достаточным признаком утвержденного дизайна.

## Implementation Decisions

- Repository workflow делится на три слоя: компактный trigger в agent instructions, каноническая человекочитаемая policy и project skill с исполняемой процедурой.
- Project skill называется `$pen-ui-contract` и срабатывает для чтения или изменения канонического `.pen`, подготовки актуальных pen.dev references, создания или изменения видимого frontend UI и проверки реализации относительно UI-контракта.
- Skill не перечисляет негативные trigger-сценарии в корневых agent instructions; подробные границы остаются внутри skill и policy.
- Глобально установленный и авторизованный `@pen.dev/cli` является prerequisite read-only режима. Установка и login не автоматизируются проектом.
- Read-only режим использует только `pen interactive`, а не CLI agent mode. Он читает последнюю сохраненную версию канонического дизайна без запуска Desktop.
- Skill содержит небольшой launcher helper, который выбирает канонический `.pen` как input, создает временный output через системный temp directory, запускает interactive CLI в PTY и удаляет временную сессию после завершения.
- Канонический `.pen` никогда не передается CLI как output. Даже явный `save()` внутри защищенной read-only сессии может записать только временный результат.
- Обычные file readers, shell-парсинг, grep-поиск и patching содержимого `.pen` запрещены. Допустимы непрозрачные файловые операции контроля вроде проверки наличия и Git status, если они не интерпретируют и не меняют внутреннюю структуру.
- Design edit режим использует только внешний MCP-сервер с именем `pencil`, подключенный к Pen Desktop. Внешнее имя сервера и namespace его tools не переименовываются.
- Перед чтением live state или изменением дизайна агент получает editor state вместе со schema и подтверждает, что активен канонический документ. Неверный файл, закрытый Desktop или недоступный MCP являются blocker без CLI/raw fallback.
- Агент изменяет design live и инкрементально, проверяет релевантную структуру, переиспользует существующие variables, reusable-компоненты и patterns и не применяет внешний style preset без явного поручения.
- Новые visual tokens, reusable-компоненты и patterns допустимы, когда существующих недостаточно, но должны быть явно показаны владельцу в ходе визуальной приемки.
- После законченной design-итерации агент проверяет затронутый layout и получает screenshot минимального релевантного screen/component. Screenshot используется экономно и не заменяет human review.
- Агент никогда не сохраняет измененный дизайн. Только владелец продукта визуально принимает canvas и сохраняет утвержденный `.pen`.
- Отдельные draft statuses, approval-файлы и стандартизированный handoff не создаются. Агент кратко сообщает, что изменения готовы и не сохранены, и ждет решения владельца.
- Если первоначальный scope включает дизайн и код, после явного подтверждения, что макет принят и сохранен, агент продолжает implementation в том же thread. Design-only поручение не расширяется до изменения кода.
- Любая задача, создающая или меняющая видимый UI, перед правкой кода читает релевантные узлы сохраненного дизайна через read-only CLI. References из spec/ticket используются для навигации, но не заменяют чтение полного контракта.
- Если нужный screen/state/component отсутствует либо design contract противоречит функциональному требованию, кодовая фаза останавливается с UI Contract Collision. Агент предлагает изменить дизайн, изменить требование или получить явное разрешение на exception.
- После frontend-реализации агент запускает обязательные repository checks из действующих frontend instructions и визуально сопоставляет pen.dev export/screenshot со screenshot работающего приложения через Playwright MCP в релевантном viewport и состоянии.
- Visual review оценивает наблюдаемую композицию, размеры, spacing, typography, colors, reusable patterns и states. Автоматический pixel-perfect diff не вводится.
- Невозможность получить screenshot нужного состояния создает visual verification gate. Владелец может закрыть его явным подтверждением собственной ручной проверки; это фиксируется только в отчете конкретной задачи и не является UI-contract exception.
- Намеренные расхождения между сохраненным дизайном и кодом допустимы только по явному решению владельца. Реестр содержит только текущие активные exceptions с причиной, design reference, областью реализации и условием удаления.
- Начальное содержимое exception registry проходит отдельный аудит против актуального дизайна, кода и принятых решений. Устраненные, устаревшие и уже не применимые записи удаляются; целевое состояние реестра — пустое.
- Нерешенные UI Contract Collisions живут в соответствующих specs/tickets, а не в глобальном exception registry.
- Статическая навигационная карта design nodes удаляется. Актуальные имена и `nodeId` всегда получают через Pencil tools, а конкретные specs/tickets продолжают фиксировать references, необходимые для реализации и review.
- Канонический design artifact, project skill, активная документация, agent instructions, specs и tickets переходят с legacy Pencil naming на pen.dev naming.
- Внешние identifiers, tool namespaces, package/source titles и несвязанные одноименные symbols не переименовываются.
- Project-scoped Desktop MCP entry с абсолютным application path удаляется. Глобальной MCP-конфигурацией управляет установленное приложение pen.dev; project skill выполняет preflight и возвращает blocker при отсутствии интеграции.
- Существующий ADR о design-as-UI-contract актуализируется: решение использовать `.pen` как визуальный источник истины сохраняется, статическая карта заменяется прямым Pencil tool access, а новый ADR не создается.
- Доменный словарь не меняется: pen.dev workflow является технической процедурой разработки, а не частью предметной модели приложения.

## Testing Decisions

- Главный seam этой работы — внешний контракт безопасного read-only launcher: при запуске он использует канонический design artifact только как input, создает отдельный временный output и не оставляет временную сессию после завершения.
- Хорошая проверка launcher рассматривает его как отдельный процесс и наблюдает сформированные аргументы и cleanup, не закрепляя внутренние shell helpers. Для изоляции допустим fake `pen` executable через `PATH`; реальный login, сеть и запуск AI-agent в такой проверке не нужны.
- Канонический `.pen` не используется как изменяемая fixture и не копируется ради экспериментальной проверки качества CLI: решение о равенстве editor engine и tools принято по официальной документации pen.dev.
- Skill проходит структурную валидацию стандартным validator для project skills: корректные metadata, trigger description, ссылки на существующие project docs и отсутствие неподдерживаемых полей.
- Repository consistency проверяется узкими поисками: активные артефакты не ссылаются на удаленную design map или старый canonical design name; допустимые внешние identifiers и исторические source titles не считаются ошибкой.
- Конфигурация Codex после удаления project-scoped Desktop MCP остается синтаксически корректной, а переносимые project MCP servers не меняются.
- Exception registry проверяется вручную против текущего кода, сохраненного дизайна и уже принятых ticket decisions. Проверка направлена на удаление лишних записей, а не на сохранение исторического списка.
- Для самой workflow-задачи product unit/component/e2e tests не добавляются, потому что наблюдаемое поведение приложения не меняется.
- Visual screenshot review через pen.dev CLI и Playwright MCP является acceptance seam будущих видимых UI-задач, а не одноразовым тестом внедрения skill.
- Если реализация helper потребует committed automated test, применяется действующий project skill для тестов; новый общий test framework только для одного launcher не вводится.
- В репозитории нет прямого prior art для shell-helper tests. Ближайший prior art — существующие project skills с компактными triggers, обязательным чтением канонических docs и targeted validation вместо проверки приватной реализации.

## Out of Scope

- Изменение продуктового дизайна, экранов, состояний или frontend-кода приложения.
- Создание нового `.pen`-макета или перенос существующего дизайна на другой формат.
- Автоматический запуск Pen Desktop из Codex или macOS wrapper вокруг GUI.
- Подключение Codex к недокументированному headless MCP server без Desktop.
- Использование CLI agent mode, batch generation, CI/CD design generation или unattended изменение канонического дизайна.
- Автоматический save измененного canvas, draft lifecycle, параллельные design tasks и отдельное хранилище approval statuses.
- Автоматический pixel-perfect visual diff и новая visual-regression инфраструктура.
- Автоматизация глобальной установки, обновления или авторизации pen.dev CLI и Desktop.
- Переименование внешнего MCP-сервера `pencil`, его tool namespace, сторонних source titles и несвязанных UI-icon identifiers.
- Создание нового ADR или добавление pen.dev терминов в предметный словарь.
- Изменение Git index, создание commit или публикация во внешний issue tracker.

## Further Notes

- На рабочей машине владельца уже установлены Pen Desktop `1.2.4` и глобальный
  `pen` CLI `0.3.2`; login выполнен. Эти версии являются текущим окружением, но
  exact version pin в repository workflow не вводится.
- Приложение pen.dev управляет глобальной Codex MCP-конфигурацией и сохраняет
  имя сервера `pencil`. Project workflow не должен пытаться переименовать этот
  внешний contract.
- Официальная документация подтверждает, что headless CLI использует тот же
  editor engine и поддерживает те же Pencil tools, что Desktop и IDE extension:
  [pen.dev CLI](https://docs.pencil.dev/for-developers/pen-cli).
- Официальный Codex workflow для live MCP требует сначала запустить pen.dev и
  открыть `.pen`: [AI Integration](https://docs.pencil.dev/getting-started/ai-integration).
- У pen.dev нет autosave; сохранение остается отдельным человеческим действием:
  [.pen Files](https://docs.pencil.dev/core-concepts/pen-files).
- После подготовки этой spec дальнейшая декомпозиция выполняется отдельным
  шагом `$to-tickets`.
