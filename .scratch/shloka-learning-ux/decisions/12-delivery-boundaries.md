# 12 — Определить границы и порядок поставки

Type: grilling
Status: resolved
Blocked by: 14 — Обновить и принять канонический pen.dev-дизайн

## Question

Как разделить согласованный UX на independently deliverable specs базового флоу и «Помощника», какие pen.dev states нужны каждому и в каком порядке их проектировать и реализовывать?

## Answer

Согласованный UX разделяется на две сквозные спецификации, каждая из которых описывает проверяемый пользовательский результат, а не отдельный frontend- или backend-слой.

Первая спецификация — «Базовый флоу заучивания шлоки». Она владеет входом в попытку и проверенным `returnTo`, загрузкой и ошибкой загрузки, status guard, основной попыткой, советами без выхода из занятия, сохранением и разрешением неоднозначного результата, завершением и осознанным продолжением. Её основной UI-контракт:

- `Заучивание — шлока` (`QPXXW`);
- `Заучивание — завершение` (`IQcqK`);
- `Заучивание — совет` (`MfM5u`);
- `Заучивание — советы исчерпаны` (`GBSHa`);
- `Заучивание — сохранение` (`qKdj4`);
- `Заучивание — ошибка сохранения` (`Ql5lM`);
- `Заучивание — результат неясен` (`LICPw`);
- `Заучивание — загрузка` (`LrbhN`);
- `Заучивание — ошибка загрузки` (`Z3V3cv`);
- `Заучивание — status guard` (`oLEhU`);
- `Заучивание — завершение без следующей` (`ak4Su`);
- `Заучивание — длинная шлока (scroll 390×844)` (`UWOdl`).

Вторая спецификация — «Помощник заучивания». Она владеет отдельным детальным DTO с четырьмя упорядоченными падами и runtime-проверкой его структурного инварианта, несохраняемым циклом из семи фрагментов и возвратом к полной шлоке. Её основной UI-контракт:

- `Помощник — прочитать` (`vh5WD`);
- `Помощник — воспроизвести` (`ZmCht`);
- `Помощник — свериться` (`AU1bg`);
- `Помощник — вся шлока` (`jejdI`).

`Заучивание — шлока` (`QPXXW`) служит для «Помощника» интеграционной ссылкой входа и возврата, но остаётся во владении базовой спецификации. Структурные пады уже хранятся в базе данных, поэтому новая DB migration для этого результата не нужна.

Спецификации готовятся в порядке: сначала базовый флоу, затем зависящий от его route/page shell «Помощник». Реализация идёт в порядке: детальный API-контракт с падами, базовая state/navigation-оболочка, UI «Помощника» и интеграция, затем общая visual- и E2E-проверка. Межспецификационный порядок фиксируется в обеих спецификациях; локальные `Blocked by` остаются только внутри собственного каталога `issues/` каждой спецификации.

Спецификации и этапы реализации разделены, но новый UX выпускается пользователям только совместно после готовности обеих частей. Это сохраняет активное действие «Помощник» из канонического `QPXXW` и не требует временного UI-contract exception или неработающего действия.
