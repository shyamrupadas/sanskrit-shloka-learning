# 05 — Определить границу данных «Помощника»

Type: grilling
Status: resolved
Blocked by: 04 — Спроектировать базовую попытку заучивания

## Question

Какой публичный контракт должен передавать «Помощнику» четыре упорядоченные пады, чтобы пошаговый UX опирался на доменную структуру шлоки, а не на неявное разбиение объединённого текста по переводам строк?

## Answer

`GET /api/library/items/{shlokaCode}` должен возвращать отдельный `LibraryShlokaDetailsDto`. Он сохраняет поля существующего `LibraryShlokaDto` и добавляет обязательное поле `padas` — упорядоченный массив ровно из четырёх непустых строк. Порядок элементов является порядком пад; отдельные идентификаторы и номера пад не нужны. Общий `LibraryShlokaDto` остаётся компактным контрактом списков, обновления статуса и завершения заучивания без `padas`.

Детальный DTO сохраняет и `text`, и `padas`: сервер гарантирует инвариант `text === padas.join("\n")`. `text` остаётся готовой проекцией для цельного отображения, а `padas` — структурным представлением для «Помощника» и других детальных сценариев. Клиент не разбирает `text` по переводам строк и не восстанавливает из него пады.

TypeSpec фиксирует обязательность и количество элементов публичного контракта, а HTTP-граница сервера проверяет инвариант во время выполнения, поскольку сгенерированные backend-типы сами не валидируют ответы. Если сохранённая шлока не содержит ровно четыре непустые пады или её `text` расходится с их объединением, детальный запрос отвечает явным `500` с `ApiError.code = "DATA_INTEGRITY_ERROR"` и безопасным сообщением без внутренних деталей. Базовый экран использует стандартное состояние ошибки загрузки; «Помощник» для таких данных не запускается, эвристического fallback-разбиения нет.
