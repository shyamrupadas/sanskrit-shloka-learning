## Реализация

- POST `/api/admin/learning/tips/{tipId}/move` принимает `direction: up | down`; DELETE `/api/admin/learning/tips/{tipId}` окончательно удаляет совет. Обе операции возвращают подтверждённый список, защищены административной ролью и описаны TypeSpec. OpenAPI, клиент и серверные типы регенерированы; генератор дополнен именованием DELETE-методов.
- Добавление, перестановка и удаление используют общую транзакционную блокировку `learning_tips`. Перестановка меняет позиции двух соседей одним UPDATE; чтение итогового списка входит в транзакцию. Сбой до commit откатывает изменения. Неизвестный ID возвращает 404, недопустимое направление/край списка — 400.
- Удаление использует существующий FK `ON DELETE CASCADE` для всех переводов; позиции оставшихся материалов не переписываются. Последний совет удаляется, общее чтение возвращает `items: []`. Seed остаётся одноразовой миграцией.
- UI обновляет только административный query cache и только подтверждённым ответом команды. На время записи повторные команды блокируются; незавершённое чтение отменяется. Ошибки порядка и удаления показаны раздельными сообщениями. Диалог называет совет, объясняет необратимость и позволяет отмену.
- Пользовательское чтение и сохранённая серия текущей попытки не изменялись; фоновой синхронизации не добавлено.
- Workflow frontend поддерживает ручной `workflow_dispatch` только для `main` и передаёт Repository Variable `VITE_ADMIN_LEARNING_ENABLED` в build. Отсутствующий флаг сохраняет прежний интерфейс; выставлять `true` можно только после проверки фактически развёрнутых API. Это ручной операционный gate, не автоматическое доказательство готовности backend.

## Завершение выпуска

Этот раздел — передача владельцу для самостоятельного выпуска. Владелец явно запретил production-выпуск в рамках задачи. Push, production-действия и смена Repository Variables не выполнялись.

1. Выпустить backend из коммита реализации через существующий backend CI/Amvera workflow. Зафиксировать source SHA, release SHA и фактическую версию Amvera. Дождаться readiness.
2. Проверить на развёрнутом API POST/PATCH советов, move и DELETE: 401 без сессии, 403 для обычного пользователя, успешный CRUD на специально созданном временном материале администратором; затем общий GET обычным пользователем. Проверить порядок и восстановить порядок исходных материалов после smoke. Не удалять реальные материалы для проверки последнего совета: этот случай защищён тестами, а live-проверку выполнять только в согласованной изолированной среде.
3. После успешного smoke выпустить frontend из того же исходного коммита и зафиксировать workflow run. Никакой переменной для включения админки нет. Workflow поддерживает автоматический запуск на подходящий push в `main` и ручной запуск; порядок фактических deployments организует владелец, общий push сам по себе его не гарантирует.
4. На выпущенном frontend пройти «Еще → Админка → Обучение», проверить создание/редактирование, порядок и удаление временного совета; проверить каталог и открытое заучивание. Зафиксировать фактические версии и результаты в отдельном отчёте выпуска. Реализация этого тикета уже закрыта по решению владельца.

**Новых DB migrations нет.** Для работы необходима миграция предыдущей спецификации `0011_learning_tips`; она должна быть применена до зависимого API. В этой задаче внешние миграции не применялись и их production-состояние не подтверждалось.

Владелец дополнительно сообщил HTTP 500 при перестановке. Лог PostgreSQL содержит `42804: column "sort_order" is of type integer but expression is of type text`. В ветках `CASE` результата перестановки отсутствовали SQL-типы параметров; добавлены `$4::integer` и `$3::integer`. Существующая executor-проверка теперь защищает явные типы и оба направления перемещения с rollback. Ошибка не требовала изменения схемы или данных. Причина соответствует [правилу PostgreSQL о типизации CASE](https://www.postgresql.org/docs/current/typeconv-union-case.html): неизвестные типы всех результатов разрешаются как `text`.
